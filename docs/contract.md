# HTTP-контракт кошелька «Советник»

Сервер принимает JSON. Суммы и лимиты — целые копейки, ставки — базисные пункты (100 = 1%). Даты определяются по UTC. `GET /healthz` проверяет доступность SQLite и возвращает `status: "ok"` и `revision`. В `revision` содержится 40-символьный SHA релиза или `null`, если SHA недоступен. Ответы `/api/` не кэшируются.

## Рекомендации и учебный каталог

`POST /api/recommendations` принимает, например, `{"scope":"mine","categoryId":"supermarkets","amountKopecks":250000}`. Сумма от 1 до 10¹² копеек. `all` сравнивает публичный каталог, `mine` — только карты текущего кошелька. Список категорий и банков: `GET /api/meta` → `{banks, categories}`; у владельца список дополнен выбранными личными категориями действующего месяца.

Ответ: `asOf`, `catalogVersion` (версия набора правил расчёта), `top3`, `allMatches`. Нет совпадений — 200 с пустыми списками; неизвестная категория, режим или недопустимая сумма — 422. Если в `mine` нет положительного возврата, поле `catalogSuggestion` может содержать одну положительную альтернативу из несохранённых карт каталога. Она не входит в личный рейтинг, записать покупку на неё без добавления карты нельзя.

На каждой карте берётся подходящее действующее точное правило; только при его отсутствии — явно заданное правило `all`. Точный ноль тоже точное правило. Проверяются порог покупки, включительная дата начала и исключительная дата окончания. При нескольких равнозначных по типу правилах выбирается наибольший возврат. Расчёт: `(amountKopecks * rateBps + 5000) // 10000`, затем ограничение `limitKopecks`, если задано. `limitApplied` сообщает, уменьшил ли лимит результат. Это оценка отдельной покупки: остаток лимита после других операций неизвестен. Сортировка — по возврату вниз, затем по ID карты вверх. `top3` — первые три строки `allMatches`.

Пример позиции для 2 500 ₽ в супермаркете:

```json
{"cardId":"B","bankName":"Учебный банк B","cardName":"Карта B","source":"catalog","categoryId":"supermarkets","rateBps":600,"limitKopecks":30000,"minAmountKopecks":1,"cashbackKopecks":15000,"limitApplied":false,"validFrom":"2026-11-01","validUntilExclusive":"2027-11-01","updatedOn":"2026-11-01"}
```

Учебная версия `training-v1` действует с 2026-11-01 до 2027-11-01 (не включительно). Супермаркеты: A — 10%, максимум 100 ₽; B — 6%, максимум 300 ₽; C — 4%, максимум 200 ₽; D — 2%, максимум 100 ₽. Минимум 1 коп. Кафе: D — 8%, максимум 300 ₽, минимум 100 ₽. На дату 2026-11-20 для примера выше порядок B (150 ₽), A и C (по 100 ₽), D (50 ₽). Импорт `python -m catalog rules.json --db advisor.sqlite3`: поля ровно как в `catalog.SEED`. Ключ `(cardId, categoryId, validFrom)` обновляется при повторе, пересечение периодов пары отклоняет пакет целиком.

## Сессия и карты

- `POST /api/auth/register` (201) и `/api/auth/login` (200): `{login,password}`; устанавливают cookie `advisor_session` (HttpOnly, SameSite=Strict, Secure при HTTPS). `GET /api/auth/me` возвращает `authenticated` и логин, если известен. `POST /api/auth/logout` очищает cookie этого клиента и возвращает 204.
- `GET /api/cards[?categoryId=…]`, `GET /api/cards/{id}` — публичный каталог и условия. `GET /api/me/cards` — сохранённые ID. `PUT`/`DELETE /api/me/cards/{id}` — добавить/убрать, 204; добавить несуществующую карту нельзя (404).
- `POST /api/me/manual-cards` принимает `{name,rules}`; каждая строка содержит публичный `categoryId`, `rateBps`, необязательные `limitKopecks`, `minAmountKopecks`. Возвращает 201 и `{cardId}`. `GET /api/me/manual-cards` — личные карты с условиями, `DELETE /api/me/manual-cards/{id}` — удалить (204). Для этих списков допускается гостевая cookie. Идентификатор владельца не передаётся в теле.
- Источник результата: `manual` — введённые вручную условия, `confirmed` — подтверждённый месячный набор, `catalog` — учебный справочник. `bankName` — известное название банка либо `null`; `updatedOn` — дата внесения условия либо `null` у старых месячных записей без даты. Начало месяца не означает, что условия обновлялись в этот день.

## Месячные наборы и план (требуется вход)

- `POST /api/me/cashback-screenshot` — `{bankId,image,cardId?}`; `image` — data URL JPG/PNG/WebP до 4 МБ. Ответ 201 — черновик `{rules,month?}`. Изображение не сохраняется; распознавание не подтверждает условия и не меняет кошелёк.
- `POST /api/me/cashback-confirm` — `{bankId,cardId?,month,mode,slots,requestId,rules}`. Месяц `YYYY-MM`, `mode` — `active` или `offer`, `slots` — целое 0–128 либо `null` (неизвестно). Строка: `label`, `categoryId`, `rateBps`, `limitKopecks`, `minAmountKopecks`, `selected`, `uncertain`. Сохраняются только явно выбранные строки с корректными числами. Подтверждение объединяет строки по буквальному `label` для данной карты, месяца и режима; непереданные строки остаются. «Кино» и «Афиша» — разные названия. Суммарное число подключённых категорий после объединения не может превышать указанное число мест; предложений для выбора может быть больше. Ошибка не сохраняет частичный набор. Неоднозначная карта банка — 409, нужно выбрать `cardId`; чужая — 404. Повтор `requestId` возвращает прежний результат; другой набор по тому же ключу — 409.
- В расчёте одной покупки участвуют только подтверждённые несомненные правила `active` текущего месяца и базовые правила карты. `offer` используется только при планировании. `POST /api/me/cashback-plan` принимает `{month,spendingMonth,spending?}`. По умолчанию использует покупки владельца в `spendingMonth`; переданный список `{categoryId,amountKopecks}` заменяет историю, в том числе при `[]`. В ответе есть `baseKopecks`, `projectedKopecks`, `gainKopecks`, `choices`, `warnings`. План не подключает категории в банке.

## Журнал и статистика (требуется вход)

- `PUT /api/me/usual-card` с `{cardId}` задаёт обычную карту только из своего кошелька. `DELETE /api/me/usual-card` или совместимый `PUT` с `{"cardId":""}` снимает выбор. Удаление обычной карты из кошелька тоже снимает выбор, не меняя историю.
- `POST /api/me/purchases` принимает `{categoryId,amountKopecks,chosenCardId,requestId?}`. Проверяет категорию до записи, принадлежность карты и применимость её условий; запоминает оценки выбранной, лучшей и обычной карты на серверную дату. Ответ 201 — `{id,calculatedKopecks,recommendedKopecks}`. Повтор записи, сделанной до появления поля `id`, может вернуть прежний ответ без ID. ID можно получить из журнала. Не читает банковские операции и не подтверждает платёж.
- Для повтора используйте `Idempotency-Key`: 16–128 ASCII букв, цифр, `-` или `_`. Старый `requestId` в теле также принимается (непустая печатная строка до 128 символов после удаления крайних пробелов, допускаются короткие ключи). `requestId: null` не отменяет заголовок. При передаче обоих ключей они должны совпадать. Тот же ключ и данные в одном аккаунте возвращают первоначальный ответ без второй записи; изменённые данные — 409. Без ключа каждый запрос создаёт отдельную запись.
- `GET /api/me/stats`: `month`, `usualCardId`, `purchases`, `count`, `calculatedKopecks`, `recommendedKopecks`, `missedKopecks`, `usualKopecks`, `versusUsualKopecks`, `note`. По умолчанию — текущий календарный месяц UTC. Опциональный query `month=YYYY-MM` ограничивает выборку указанным месяцем текущего пользователя; неверный формат — 422. Если хотя бы для одной покупки нет оценки обычной карты или покупок нет, сравнение с обычной картой — `null`, а не ноль. `POST /api/me/stats/comment` запрашивает необязательное текстовое пояснение `{comment}`; недоступность внешнего сервиса — 502 и не влияет на сохранённые покупки.

## План нескольких покупок

`POST /api/me/purchase-plan` сравнивает от 2 до 8 покупок по картам текущего
кошелька. Поддерживает гостевую и авторизованную сессии. Категории принимает из
`/api/meta`, суммы задаются целыми копейками. План применяет правила, действующие
на дату расчёта, и остатки общего лимита каждой карты за текущий месяц UTC.

```json
{"purchases":[{"categoryId":"supermarkets","amountKopecks":100000},{"categoryId":"transport","amountKopecks":100000}]}
```

Ответ содержит `month`, `optimized`, `sequential`, `gainKopecks` и
`assumedFullCardIds`. В обоих вариантах возвращаются `totalKopecks` и массив
`purchases` в исходном порядке. Каждая строка содержит `cardId`, `cardName`,
`bankName` и `cashbackKopecks`. При отсутствии положительного возврата
поля карты равны `null`, сумма равна нулю.

`sequential` выбирает самый высокий возврат по очереди, уменьшая расчётный
остаток после каждой покупки. `optimized` максимизирует сумму за весь список.
При равных итогах возвращается тот же выбор, что и в `sequential`. Покупка
целиком относится к одной карте. При заданном лимите и неизвестных начислениях
расчёт предполагает полный остаток, а идентификатор карты указывается в
`assumedFullCardIds`. План не записывает покупки и не расходует сохранённый лимит.


### Объяснение результата плана

`explanation.code` принимает `same_total`, `shared_limit` или
`better_allocation`. `changes` содержит только изменившиеся покупки с
`purchaseIndex` (с нуля), строками `optimized` и `sequential` и разницей
`deltaKopecks`. Для `shared_limit` дополнительно возвращаются
`cardId`, `cardName`, `reserveFromPurchaseIndex`, `useAtPurchaseIndex`
и `savedBalanceKopecks` — сколько остатка сохранилось на этой карте к моменту
следующей указанной покупки. `assumedFullCards` добавляет имена карт к
`assumedFullCardIds`.

Например, в супермаркете и транспорте по 1 000 ₽ карта А даёт 10% с общим
остатком 100 ₽. Карта Б даёт 8% и 1% соответственно. Итог плана 180 ₽,
последовательного выбора 110 ₽. Код `shared_limit`, индексы 0 и 1, разницы
по покупкам −2 000 и +9 000 копеек.

## Сверка остатка по карте

1. `GET /api/me/stats` возвращает в каждой покупке `id`, `cardId` и
   `actualCashbackKopecks`. `null` означает, что пользователь ещё не внёс
   фактическое начисление. `PUT /api/me/purchases/{id}/cashback` принимает
   `{"amountKopecks":8000}` (204). Передача `null` удаляет отметку,
   а 0 подтверждает нулевое начисление.
2. `GET /api/me/cards/{cardId}/cashback-reconciliation` возвращает за текущий
   месяц UTC `month`, `cardId`, `reconciledAt` (ISO 8601), исходный
   `bankRemainingKopecks`, `deductedKopecks`, `remainingKopecks` и
   `accruals`. До первой сверки дата и суммы сверки равны `null`.
   В `accruals` только фактические начисления по покупкам этой карты за
   текущий месяц. Каждая строка содержит `purchaseId`, `cardId`, `date`,
   `categoryId`, `purchaseAmountKopecks`, `actualCashbackKopecks`
   и `includedInBankBalance`.
3. На тот же адрес отправляется `PUT` со всем набором отметок.
   Например, при начислениях 50 и 80 ₽ покупка 17 уже входит в остаток банка.

```json
{"month":"2026-11","bankRemainingKopecks":30000,"includedPurchaseIds":[17]}
```

Ответ 200 в формате GET. В примере `deductedKopecks` = 8000, а
`remainingKopecks` = 22000. Повтор с теми же данными сохраняет дату.
При новой сверке указываются новый остаток и все вошедшие в него начисления.
Подтверждённые начисления, которые ещё не учтены банком, вычитаются из
переданного остатка, минимум до нуля. Расчётные суммы из журнала не участвуют.
Сверенный остаток имеет приоритет над прежней ручной настройкой лимита на
этот месяц и используется в обычной рекомендации и плане покупок.
Для записей журнала используется месяц покупки. Валидный остаток 0 ₽
остаётся известным остатком. При смене месяца прежняя сверка не применяется.
Смена месяца или отметки недоступных начислений по своим покупкам дают 409,
например `{"message":"Список начислений изменился. Откройте сверку заново"}`.
После 409 загрузите список заново через GET и перепроверьте отметки перед PUT.
Функции сверки и фактических начислений требуют входа. Чужая или несуществующая
карта или покупка даёт 404, в том числе покупка, переданная в `includedPurchaseIds`.

## Месячная сводка кэшбэка

`GET /api/me/stats?month=YYYY-MM` подходит для виджета сводки. По умолчанию
используется текущий месяц UTC. Ранее возвращаемые поля и порядок карт сохранены.

| Поле | Значение |
|---|---|
| `count` | Покупки, записанные в КопиКэше за месяц. |
| `actualCashbackKopecks` | Сумма фактических начислений, внесённых пользователем. `null` при отсутствии подтверждений. |
| `actualCashbackCount` | Покупки с внесённым начислением, включая подтверждённые 0 ₽. |
| `calculatedKopecks` | Ожидаемый возврат по выбранным картам на момент записи покупок. |
| `missedKopecks` | Разница между сохранёнными оценками лучшей и выбранной карты по тем же покупкам. |
| `cards[]` | `cardId`, `name`, `count`, `spentKopecks`, `cashbackKopecks` (расчётный), `missedKopecks`, `actualCashbackKopecks` и `actualCashbackCount` для каждой выбранной карты. |

Редактирование или удаление подтверждённого начисления отражается при следующем
запросе. Начисление относится к месяцу покупки. Сверка банковского остатка
и изменения текущих ставок не пересчитывают сохранённые оценки.

## Подтверждение покупки и Web Push

Черновик создаётся явным действием «Выбрать для оплаты и подтвердить позже» после расчёта и выбора карты. Для записи сразу остаётся кнопка «Записать покупку» и прежний `POST /api/me/purchases`. До подтверждения черновик отсутствует в журнале и месячных итогах.

| Запрос | Назначение |
| --- | --- |
| `POST /api/me/purchase-drafts` | Создать черновик. Тело содержит `requestId` (например UUID), `categoryId`, `amountKopecks`, `chosenCardId`, `timezone` (IANA, по умолчанию UTC). Повтор запроса с тем же ключом и данными возвращает исходный черновик. |
| `GET /api/me/purchase-drafts` | Вернуть `{drafts: [...]}` с незакрытыми черновиками владельца. |
| `GET /api/me/purchase-drafts/{id}` | Вернуть любой черновик владельца, включая закрытый. Глубокая ссылка `/?draft={id}#home` переживает вход. |
| `PUT /api/me/purchase-drafts/{id}/decision` | Принять `{"action":"confirm"}`, при необходимости с `amountKopecks`, `chosenCardId` и `paidOn` формата `YYYY-MM-DD`, или `{"action":"decline"}`. Повтор решения возвращает сохранённый результат. Другое решение по закрытому черновику возвращает 409. |
| `GET /api/me/push` | Вернуть `{publicKey}`. Значение `null` означает, что доставка на стенде выключена. |
| `PUT /api/me/push` | Подключить уведомления по `PushSubscription.toJSON()`. |
| `POST /api/me/push/status`, `DELETE /api/me/push` | Проверить или выключить подписку текущего устройства. Тело содержит `endpoint`. |

Черновик возвращает `id`, `status` (`pending`, `confirmed`, `declined`), `categoryId`, `amountKopecks`, `chosenCardId`, `paidOn`, `remindAt` (UTC), `purchaseId` (до подтверждения `null`) и `cards: [{id, name}]`. Запрос к чужому черновику возвращает 404. Подтверждение и запись в журнал выполняются одной транзакцией, фактический кэшбэк остаётся `null`. Месяц определяется датой оплаты. Для исходной даты расчёт использует ставки и лимиты из снимка на момент выбора. При смене даты или отсутствии подходящего правила для выбранной карты журнал показывает «Расчёт недоступен». В API это `estimateAvailable: false`, числовые поля для суммы оценки сохраняют тип и принимают 0, поэтому покупка не добавляет прогноз к месячному итогу.

### Дизайн и приёмка

- В блоке «Подтверждение покупок» на главной показываются независимые черновики. На карточке есть «Да, оплатил», «Нет, не оплатил» и «Изменить» с суммой, картой и датой. Закрытие карточки оставляет черновик.
- Пуш создаётся только после разрешения на устройстве. На следующий день в 12:00 по часовому поясу черновика планировщик делает одну попытку доставки на последнее подключённое устройство. В уведомлении «КопиКэш» показан только текст «Подтвердите покупку, если вы её оплатили». При недоставке, отказе в разрешении или без подписки подтверждение доступно на главной.
- Для закрытой покупки ссылка показывает результат без повторной записи. Для ошибки запроса форма сохраняет введённые данные.

Для HTTPS-стенда задайте окружение процесса `ADVISOR_VAPID_PUBLIC_KEY` (публичная точка P-256 в base64url), `ADVISOR_VAPID_PRIVATE_KEY` (секретный скаляр P-256 в base64url) и `ADVISOR_VAPID_SUBJECT` (например `mailto:push@example.org`). SQLite создаёт таблицы при запуске. Нужен исходящий HTTPS к браузерным push-службам. На iPhone и iPad пользователь включает уведомления из приложения, добавленного на экран «Домой».

На чистой базе прогоняются `python -m unittest test_purchase_reminders -v` и `python tests/browser_mvp.py`. Доставка на телефоны проверяется отдельно на HTTPS-стенде с VAPID. Для ускорения на тестовой базе можно сдвинуть `wallet_purchase_drafts.remind_at` на текущий UTC и дождаться ближайшего прохода планировщика.
